# Retention 58: complete preservation of 34 generated request-identity records

Date: 2026-11-28. Status: a source and parameter preservation operation, not a scientific result. Root is the sole publisher and decides when the exact listed files are removed by an ordinary commit.

## 1. Exact scope

This batch contains 34 small JSON wrappers written by the original public Actions verification steps. Their total current-tree size is **232,591 bytes**. The fixed recovery commit is `18081452c5181d958bb5432c4045c067bf1d1caa`; its complete topic-tree identity is `a586acc6f2098a5f5a0e49cbfb3f523ec189129c`. Every selected path, Git blob and byte count was matched at this commit. Root must use the exact deletion entries, rather than a filename pattern, when merging with its current main.

The selection consists of ten early condensed-followup request bindings, thirteen completed-readback request bindings, four direct-LD or damped-chain request bindings, and seven bindings for original576/current576/noJ/word-first/model-response/realized-trial lanes. The complete list, including whole SHA-256, is in `computations/legacy-request-identity-retention-58-provenance.json`.

This batch removes no source, proof, original request, parameter file, spec, numerical raw, checkpoint, status, actual summary, scientific result note or current-run material. It does not modify any solver, queue, target, seed, tolerance or budget. This is the scope of this batch; it is not a new restriction overriding the root README's rule 15 for later independently documented retention operations.

## 2. What was actually read

All 34 original wrappers were read in full. For each one, the original workflow was fetched at the wrapper's actual `source_commit`, not from a later same-name workflow at main. There are 30 distinct complete original workflow versions. Each own wrapper basename occurs once in its original generating workflow, at the actual JSON write in the input/source verification step before that workflow's later worker or completed-readback invocation.

All 34 original request files were independently fetched at their actual source commits. The whole UTF-8 SHA-256 equals the original wrapper's `request_sha256`, and the complete parsed request, including object key order, equals the wrapper's saved request. The ledger records all eleven original request paths, their exact byte counts and Git blobs, and the corresponding workflow versions.

The wrappers contain 145 distinct original verified-source identities. Every one was statted at its actual historical source commit and its exact path and byte count matched the recovery object. The original whole-source SHA remains the original Actions verification record. This operation did **not** reread all 145 scientific source bodies or claim a fresh scientific-source audit. The actual writer is the complete workflow, whose small full text and whole identity were read.

No file at or above 100,000 bytes and no binary body was read. No local mathematical computation, solver, AST, fixture or benchmark was run.

## 3. Lossless complete field preservation

The 97,038-byte file `computations/legacy-request-identity-retention-58-complete-parameters.json` preserves every decoded JSON value from all 34 original wrappers. It retains every nested request field, verified source, input or artifact tuple, budget, original failure record, source commit, README blob, flag and object key order. Only repeated strings and repeated containers share storage. No setting or provenance branch was removed to fit a size limit.

The encoding is explicit in the file. Literal null, booleans and numbers remain literal. A string reference is `[0,i]`; an original array is `[1,...]`; an original object is `[2,keyStringIndex,value,...]`; and `[3,i]` refers to the previously defined container at index i. Each container uses only earlier container references. Every original root value has its own record and exact byte-recovery identity.

All 34 decoded objects were compared with their fully read original parsed objects using complete serialization in preserved key order; they matched. This comparison is a performed storage operation, not a new requirement before any scientific run.

This encoding preserves JSON values and key order. It intentionally does not claim to preserve original whitespace or number-token spelling. In particular, neither the original wrapper's whole SHA nor its original request-byte SHA is the hash of a newly serialized object. An old exact-byte reader receives the original Git object, not this compact parameter document.

## 5. Readers and exact restoration

There are historical byte-audit readers which consume a `completed-readback-request-identity.json` or an original request at its exact historical path. The ledger preserves the complete identities of `read_actual86_complete_receipt_bytes.py`, `read_actual89_primary_bytes.py` and `root_20261115_read_actual94_primary_bytes.py`. The one-write fact in a generating workflow does not imply the absence of later readers.

To reproduce an original reader, first restore the original wrapper into the path that reader actually opens:

```sh
git show 18081452c5181d958bb5432c4045c067bf1d1caa:topics/visible-flex-larger-amplitude/notes/public-actions-43627827085-1-condensedqp/followup-request-identity.json
```

The corresponding exact blob is recorded in its deletion entry. Restore original request and source files from their own recorded source commits, not from the retention commit or current main. Restore the complete original workflow version for its exact command and resource contract. This is an explicit replay mapping, not a change to the old reader or an assertion that new JSON bytes pass an old hash guard.

All scientific inputs, outputs, raw/checkpoint/status records and the reader sources remain untouched in this batch. Ordinary Git history retains the original wrapper objects. No history is rewritten and no force push is involved.

## 6. Actual outcomes are preserved

Twenty-one complete small result notes were read and their exact identities are retained in the ledger. They stay in the tree unchanged. Their distinctions matter:

- Request 52 failed before its direct-LD worker because of spec transport. Request 54 computed its direction but its later trial launcher hit the original plain-versus-gzip path failure.
- Request 55's ten attempts failed inside evaluation; they are not ten completed nondecreasing residuals. Request 57 did complete ten recorded trial norms, all identical at the retained words, and accepted no trial.
- Request 59's accepted first noJ trial remains an actual accepted trial, while Infinity placeholders are not newly proved positivity margins. Request 61's actual J/QR and noJ progress did not complete its native target or final tail/endpoint-J/audit.
- Request 65's pre-evaluation digest failure remains separate from its exact retry and conditional response. Request 73's line-search failure, request 83's full but nondecreasing noJ trial, and request 95's scientific failure despite successful publication are not promoted into completed solutions.
- The ten condensed continuations retain their accepted warm steps and their original nonlinear/domain limits. They do not become complete BVP/native/research-goal success.

The thirteen completed-readback wrapper records preserve their full requests and flags. This storage operation does not claim to have newly rerun their diagnostics or independently re-established every later numerical result.
